Doing without the thermocouple

An earlier revision of this firmware shipped three fan modes. Reading its own 225-minute run back showed they were one control law with a different constant — the die observer is a setpoint transformation, not a feedback element — so the modes collapsed into a single loop with one regulated quantity, the estimated on-die temperature, and made the thermocouple substitutable while power became mandatory. A model now exists, fitted from four earlier runs, so this is the first time that substitution could actually be measured rather than merely enabled: three arms, same setpoint, same load, differing only in where the loop's one temperature comes from — the sensor, a fitted estimate of it, or nothing at all. At steady state it costs nothing that this rig can detect. Closing the loop on the estimate put the fan within — of where the sensor put it — far below the actuator's own 1.587 % resolution — and the regulated temperature within — once the drift the fan-off brackets measured is taken out, against a — repeatability floor carried forward from the previous run of this plan. The cost is in the approach: the estimate lags a warming heatsink, so the loop under-cools it, reaches the setpoint — early and overshoots — further. One pole is enough to hold a setpoint and not enough to arrive at one.

Key findings

What was asked of it

One plan, one model, one card, one setpoint. The only thing that changes between the three arms is where the loop's single temperature comes from — so a difference between them is the sensor and not the workload.

0.6.0 reports which of three sources the loop actually used, in ctl.src: measured (the physical thermocouple, closed loop with the PI), inferred (a learned estimate of it, also closed loop with the PI), or none (open loop, the static feedforward alone and no PI at all). The control law is identical in the first two; only where tc_ comes from changes. That is the architectural claim being tested — a soft sensor is a drop-in for one input, not a second controller — and it is why the three arms differ in two plan keys and nothing else.

Why 90 °C and not the auto 95: arms 2 and 3 have either no feedback or feedback through an estimate, and the Hailo-8's throttle boundary is hysteretic and stochastic — observed anywhere from 98.9 to 104.2 °C. Five degrees of margin lets an open loop be wrong without inviting a throttle into the measurement.

Did each arm run as configured?

This table comes first, not last. The log records what the loop did, never what the plan asked for, so ctl.src and ctl.state are the only evidence an arm was the arm it claims to be. This is the first run in which all three arms are genuinely distinct — a model is compiled in, so arm 3 got what it asked for.

Arm 3 reports ctl.src = 1 modelled, and that is the whole point of the run. On the 23 November run of this same plan there was no model compiled in, so arm 3 fell through to open loop and was separated from arm 2 by ctl.state alone — 5 open against 6 degraded. A model now exists, ctl.model_ready reads 1 on every row, and the request in ctl.tc was honoured. This is the first log on this rig in which the fan was driven by an estimate rather than a measurement.

The column that makes that legible had to be fixed on hardware, not in review. As first written, the NaN check on the modelled estimate sat after the if/else rather than inside its branch — and pv_tc is NaN in the none branch too, so the check fired unconditionally and every open-loop step reported degraded. kOpen was unreachable. A staged bench test caught it in one command; nothing in the code read wrong. Had it shipped, the earlier run would have measured arm 2 three times with no way to say so — and this run could not have proved that arm 3 was different.

What losing the sensor actually costs

Not the regulated temperature — the estimate. In the closed-loop arm the board's die model is anchored to a live measurement, so the fan's own quantisation does not move it. In open loop the model is computed from the applied duty, so every 1.587 % EMC2101 step swings it directly.

The board's model minus the card's own sensor

Settled windows only. In open loop die_est tracks the setpoint by construction while the fan is unclamped, so pooling the approach would report a 42 °C "error" that says nothing about the model.

Which fan levels each arm actually sat on

The duty is the board's own readback, never the requested percent. The EMC2101 quantises to 1/63, so an arm's mean duty hides which levels it actually dithered between.

What the substitution costs

The question the whole plan exists to answer. Arms 1 and 3 are both closed loops running an identical control law at the same setpoint on the same load — only where tc_ comes from differs. Arm 1 reads the thermocouple; arm 3 reads a fitted estimate of it. A soft sensor is a drop-in for one input, not a second controller, and this is the measurement of that claim.

How much of that can we believe?

This run cannot measure its own noise floor. All three arms are distinct configurations now, which is the point of it — but it means there is no replicate pair. The bound is therefore carried forward from the 23 November run of the identical plan, where arms 2 and 3 both ran open because no model existed, making them an accidental replicate pair. It is computed from that file rather than typed in. No difference in this report may be called real below it.

The four fan-off brackets, and why they are 30 minutes each

Before the first arm, between each pair, and after the last, the plan hands the fan register back and holds the duty at 0 with the card at idle — a fixed ~0.86 W and no forced air. Repeated four times across three and a half hours, that is an ambient probe, and it is the only instrument in the run that can tell a hardware change from a controller difference. It cost nothing but time, and this run needed it.

The EMC2101 is not an inlet sensor, and this is the first run where that mattered. It is the fan controller's own die temperature — it has self-heating, it reads in 0.25 °C steps, and it sits on the probe board rather than in the airstream. The feedforward uses it as air, which is fine while the loop has a thermocouple to close on. Open loop has nothing to correct it with, so a quarter-degree of unmeasured inlet shift flips one EMC2101 duty level, and one level is most of a degree of die.

One constant, three failures retired

The earlier firmware's run produced three different-looking failures from one defect: the tracking error during any approach is model error plus the heatsink has not got there yet, and nothing separated them — so the PI demanded the fan compensate for the thermal time constant. 0.6.0 bounds the PI's authority instead of adding more anti-windup, because the integrator was unwinding correctly from a value the loop could never use.

const double corr = clampd(kp * err + integ, -kTrim, kTrim);   // kTrim = 15 duty points
const double raw  = base + corr;
const double out  = clampd(raw, min_duty, max_duty);
integ = clampd(integ, -kTrim - kp * err, kTrim - kp * err);     // give back what the window cannot express

An integrator above 15 is legal, and counting it as windup would be a misreading. The bound is ±kTrim − kp·err, not ±kTrim — so when the error is −40 the integrator is allowed up to +55, and it is holding exactly the demand the trim window cannot currently express. What is bounded is the sum: the PI may move the feedforward by at most 15 duty points, whatever its internal state. — samples of this arm sat above kTrim and not one of them reached the fan.

Scoring the board's model of the die

The board cannot read the die. It regulates heatsink + Rint × watts with Rint = 1.709 °C/W, and the card's own sensor sits in the same row of the same CSV — so every run tests that figure for free. This one tests it three ways, because the three arms build the estimate differently.

Rint stays at 1.709, and this run cannot improve on it. All three arms held the same setpoint at the same load, so they land within — duty points of each other — one operating point. an earlier four-setpoint run measured 1.619 °C/W at 32–41 % duty against 1.742 at 58–61 %, i.e. Rint is a loaded operating-point resistance and not a paste constant; duty and heatsink temperature are confounded across those points too. Separating them needs one setpoint held at two different loads, which no run so far has done.

The feedforward, spot-checked

The duty the loop asks for first comes from inverting a nine-point Rconv table in Control.h. This run re-measures it at one duty, so it is a spot check and not a recalibration — but it is a spot check taken with the hardware at rest rather than five minutes into a tread. The table was refitted on 24 November, after this run: its three lowest nodes came from the fan ladder's throttled treads and were wrong by up to 32 %. Nothing at or above 30.2 % duty moved by more than 1.1 %, and all three arms here sat near 37 %, so the spot check below is unaffected either way — see the soft sensor.

Throughput, and the margin that was never spent

The board cannot see the core clock or the frame rate — those are PCIe-side, host-only. So the loop holds a die temperature believed safe; it cannot detect throttling and react. The host logs both, which is what lets any setpoint be audited after the fact.
